# CHP-VTok 原生 1080p 长程训练首轮结果

日期：2026-11-15。此报告追加到既有工程验证，保留原有实验。模型代码基线 `f481cb6`，运行流程提交 `127d41a`，此前阶段指标归档提交 `5a27fc4`。

**本轮完成从 Multi step 44 到 step 1044 的 1000 次新增优化更新，以及三个固定时间留出片段的四预算验证。它证明了这一小数据条件下可测的重建改善，不代表足量数据训练、跨视频泛化、收敛或实时验收已经完成。**

## 训练与数据

- 训练及阶段评估于北京时间 00:13:23 开始，11:53:52 完成，历时约 11 小时 40 分钟。全部 19 个训练/评估任务退出码为 0。数据准备另计；第一次准备命令因 PYTHONPATH 缺失失败，重试成功，原日志保留。
- 1000 个训练记录编号连续为 45–1044，所有输入均为 `[1,3,17,1080,1920]`，所有 loss 有限。峰值 allocated 为 65.505 GB；这与 allocator reserved 及 nvidia-smi 占用不同。
- 继续使用原 InfoTok Trainer、优化器、scheduler 和 checkpoint manager。冻结卷积骨干，训练 1D 压缩器、恢复器和因果条件模块；每个历史块独立随机预算。
- RGB 与时间损失使用完整原生视频。训练感知损失采样真实 256×256 像素区域、不缩放；评估 LPIPS/DISTS 使用完整原生帧和原始 FP32 RGB 参考，模型推理精度为 BF16。
- 三个只读源共提取 591 个训练帧和三个各 17 帧的时间留出片段；源帧范围之间隔 16 帧。仅三个相同场景，留出片段不等于跨视频独立测试集。精确范围、逐帧计数与首帧 RGB 一致性验证见 `data_split.json`。

## 后训练工程验证

step1044 在 MCL 同源时间留出片段上补测，输入为原生 `[1,3,17,1080,1920]`，混合预算 `[256,512,1024,2048,256]`。结果见 `posttrain1044/acceptance.json`：

| 检查 | FP32 | BF16 |
|---|---|---|
| Encoder 未来干预：过去 ID | 全等 | 全等 |
| Decoder 未来干预：过去 RGB 最大差 | 0 | 0 |
| 完整 vs 合法历史重算 ID | 全等 | 全等 |
| 完整 vs 真缓存 ID | 全等 | **58/10240 变化（0.5664%），未通过** |
| 完整 vs 真缓存 RGB 最大/平均差 | 1.669e-6 / 1.156e-7 | 0.03125 / 0.000808716 |

第一次 FP32 整窗干预补测在第二次完整解码时因 allocator 碎片 OOM，原失败日志保留。使用独立进程与 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 重跑成功；不改变输入、权重、算子定义和块协议。这是运行时分配策略变化，其显存/延迟不应被误归因为模型架构优化。缓存编码/解码实测为 FP32 6.456/25.859 s，BF16 4.356/16.155 s；两者均不实时。该数值验证限于本 17 帧样本。

用同一训练 checkpoint 导出全新公开 Decoder，在独立进程做真实 TCP loopback：

| 发送策略（含 Bootstrap） | 实际字节 | 含进程启动总耗时 | Receiver ID |
|---|---:|---:|---|
| 每块 256→512→1024→2048 | 21601 | 56.741 s | 与 Sender 全等 |
| 各块最终预算 256,512,1024,2048,256 | 9034 | 42.004 s | 全部已收前缀与 Sender 全等 |

两次 Receiver 访问审计均为 `raw_video_access=false`、`sender_latent_access=false`。它们只读取新公开 Decoder 和收到的码流；不将应用层审计宣称为恶意进程的 OS 隔离。第一组的第一个四帧块在各增量预算的端到端时延约 14.763/16.442/18.121/21.436 s，定义为同机单调时钟下从该块编码开始到 RGB 就绪、包含排队。源 17 帧事先可用，不是直播采集或 WAN 结果。

本轮没有重新运行与模型权重无关的全部单元测试；历史 91 项回归及本次权重相关的 GPU 集成证据分别保留，不合并成虚构的新测试计数。
